## State hoisting
State hoisting in Compose is a pattern of moving state to a composable's caller to make a composable stateless.
Advantages:
- Single source of truth
- Encapsulated
- Shareable
- Decoupled

## Scroll Behaviour

- **listState** = rememberLazyListState(): contains information about LazyColumn
- **snapshotFlow**: converts Compose state reads into a Flow.

```
// controlling visible item

val listState = rememberLazyListState()
LaunchedEffect(listState) {  // collect is a suspend function
    snapshotFlow {  
        val layout = listState.layoutInfo.visibleItemsInfo // get all visible Items
			.map { it.index }  // from Items, get only index
			.toSet()  // convert to Set
	}.collect { visibleIds ->  // collect Flow values over time
		viewModel.onVisibleRowsChanged(visibleIds)  
	}  
}
```

```
// Infinite scrolling implementation

LaunchedEffect(listState) {  
    snapshotFlow {  
        val layout = listState.layoutInfo  
        val lastVisible = layout.visibleItemsInfo.lastOrNull()?.index ?: 0  
        lastVisible to layout.totalItemsCount  // return a Pair[lastVisible, totalCount]
    }  
        .map { (lastVisible, total) ->  // Pair get transform using map
            total > 0 && lastVisible >= total - 5  
        }  
        .distinctUntilChanged() // remove duplicate triggers when scrolling near the end  
        .collect { shouldLoadMore ->  // collect Boolean value
            if (shouldLoadMore) {  
                viewModel.loadNextPage()  
            }  
        }  
}
```



## Side-effects
**remember(key)**: recomposition optimization, only recompute when **key** value **change**
Used **frequently** because it minimize expensive calculations

**rememberSaveable, rememberSearializable(key)**: survice recompositon, activity recreation, process death.
Used for user input, scroll state, toggles
Data type must be serializable

**LaunnchEffect(key**: side-effect that runs a suspend function in response to changes in the composition.
Used in the scope of a composable and as a coroutine. Key is also parameter to determine relaunch
Used for: running suspend func, loading data, reacting to state changes, navigation events

**rememberUpdatedState(capturedValue)**: reference a value in an effect(LaunnchEffect) that shoudn't restart if value changes.
Use this when you want to capture **value**, and you don't want the effect to restart because of that **value**
Example
```
// This will always refer to the latest onTimeout function that
// LandingScreen was recomposed with
val currentOnTimeout by rememberUpdatedState(onTimeout)

// Create an effect that matches the lifecycle of LandingScreen.
// If LandingScreen recomposes, the delay shouldn't start again.
LaunchedEffect(true) {
	delay(SplashWaitTimeMillis)
	currentOnTimeout()
}
```

**rememberCoroutineScope**(): obtain a composition scope to **launch coroutine outside a composable**
Used for: handling triggers/user action, animation
```
val scope = rememberCoroutineScope()

    Button(
        onClick = {
            scope.launch {
                viewModel.loadUser()
            }
        }
    )
```

**derivedStateOf**: a computed state that only updates **when** its **dependent** values actually change.
**Basically**, the state of A depend on state of B
**Benefit**: recompute ONLY when dependencies meaningfully change - avoid expensive recomposition(ex: when B is a list, scroll can be expensive)
Don't overuse it
```
val isButtonEnabled by remember {  
	derivedStateOf {  
		username.isNotBlank() && password.isNotBlank()  
	}  
}

val showButton by remember {
    derivedStateOf {
         listState.firstVisibleItemIndex > 0
    }
}
```



**DisposableEffect**(less common): Effects thar require cleanup
Used for:
- register/unregister listeners
- lifecycle observers
- sensors

**SideEffect**(less common): publish Compose state to non-Compose code(analytics, logging, external object)
Usef for:
- analytics
- logging


# UI Performance

## Layout Inspector
 What to look for
- Recomposition count increasing constantly.
- A composable recomposing even when its data didn’t change.
- Large parts of the UI recomposing when only one small state changes.

## System Tracing
This shows:
- Frame timeline
- Main thread work
- Render thread
- GPU work
- Choreographer events

### What is “good”?
Android renders at 60 FPS.
- 16.6 ms per frame budget
- If a frame takes 25 ms, the UI stutters.
- If it takes 40+ ms, users will notice.


## Macrobenchmark
This is how you measure startup, scrolling, and animations automatically.
```
androidTestImplementation(
    "androidx.benchmark:benchmark-macro-junit4:1.2.4"
)
```

## JankStats (runtime monitoring)
Google provides JankStats to detect dropped frames on real devices.




# Adaptive Dynamic Screen Design

### Current way to check screen size
```
val windowSize = currentWindowAdaptiveInfo().windowSizeClass  
  
val isAtLeastMediumWidth = windowSize.isWidthAtLeastBreakpoint(  
    WindowSizeClass.WIDTH_DP_MEDIUM_LOWER_BOUND  
)  
  
val contentType = if (isAtLeastMediumWidth) {  
    ContentType.LIST_AND_DETAIL  
} else {  
    ContentType.LIST_ONLY  
}
```
